# Web 前端协作规则

## 适用范围与当前阶段

本文件适用于 `apps/web/`，与根目录 [AGENTS.md](../../AGENTS.md) 一起遵守。全局需求、跨服务契约和架构决策仍以根规则指定的来源为准。

当前保留 Vue Router 4 公共外壳和 M2/M3 静态说明入口，m1 分支已按具体任务接入 M1 与 D-02 业务页面和公共认证消费接口。真实 D-01 身份提供方尚缺失，开发身份必须显式开启；实现、替身、验证与部署范围以各模块 STATUS 为准。原骨架记录见 [前端骨架任务](docs/frontend-scaffold.md)。新增业务仍须具体任务，不为补齐目录创建假实现或安装无关依赖。

开始任务时读取 [模块交接索引](../../docs/module-status.md)、本模块和后端提供方的 `STATUS.md` 及相关契约。完成业务模块任务时，更新 `src/modules/<module>/STATUS.md`；涉及公共布局、组件、登录或请求基础设施时，更新 [Web 公共记录](STATUS.md)。前后端完成程度分别记录，接口尚未接入时必须明确写出；不能把静态说明页或构建通过当作业务已完成。

仅在本任务需要其他业务模块或 D 等公共部分协作时，按根规则尝试同步 develop。其他业务模块功能缺失时，在本模块记录依赖缺口和影响，不代改对方前后端代码、测试、规则或状态文件；同一业务模块的前后端仍按任务范围衔接。D、公共布局和公共请求等共享部分可按任务的明确需求及验收条件修改，并遵守公共变更评审规则。

## 模块目录与依赖方向

保持一个 Vue 应用，业务代码按模块组织：

```text
src/
  modules/
    m1/                  # 座位搜索、预约、签到等
      pages/
      components/
      api.ts             # 首个已评审业务接口任务再创建
      routes.ts          # M1 页面路由
    m2/                  # 整室申请与审批；沿用相同组织方式
    m3/                  # 报修与维修工单；沿用相同组织方式
  shared/
    components/          # 可复用的展示与交互组件
    layouts/             # 导航与页面框架
    api/                 # 公共 HTTP 配置和错误处理
    auth/                # 登录状态与公共权限展示逻辑
  router/
    index.ts             # 模块路由汇总
  App.vue
  main.ts
  style.css
```

- M1、M2、M3 组分别维护 `src/modules/m1/`、`m2/`、`m3/`。模块独有的设计、实现和测试说明也放在对应目录；有额外代理约束时，在该目录添加局部 `AGENTS.md`。
- 业务模块可以依赖 `src/shared/`；公共代码不得导入 `src/modules/` 内部实现。模块之间通过明确的路由、参数或公共接口协作，不直接导入对方的页面、私有组件或业务状态。
- D 的管理页面须按具体任务和已确认的 D 子域责任安排；D 业务不能因供多模块使用就全部放进 `shared/auth/` 或公共组件。
- 页面组合、筛选和展示逻辑放在所属业务模块。公共 HTTP 层只处理请求基础设施，不承接各模块的审批、预约或工单业务判断。

## 修改责任与公共文件评审

| 修改范围 | 协作要求 |
| --- | --- |
| 模块内的页面、组件、接口适配、路由和说明 | 对应模块组负责；任务明确允许修改的目录和验收条件 |
| 公共组件、布局、登录和 HTTP 基础设施 | 任务或 PR 明确维护与集成人，受影响的消费模块参与评审 |
| `App.vue`、`main.ts`、根路由、导航、全局样式 | 作为公共入口协调变更，避免各模块重复搭建或同时改写整份文件 |
| `package.json`、`package-lock.json`、Vite/TypeScript 配置 | 说明必要性和影响，协调修改；依赖清单和 npm 生成的锁文件保持一致 |
| Web Dockerfile、Nginx、Compose 和流水线 | 属于跨模块工程配置，与部署维护者及受影响模块共同评审，遵守根规则 |

这些规则约定责任，不指定具体个人。共享改动须在任务或 PR 中列出负责集成和评审的人员或组，以及受影响的模块。代理可在已授权任务范围内准备改动，评审在请求合并前完成。

根路由汇总各模块导出的路由，约定 `/m1/*`、`/m2/*`、`/m3/*` 页面范围。公共布局接收导航参数，应用入口负责组合导航和路由视图。后续新增模块内页面优先修改本模块的 `routes.ts`；涉及导航或公共入口时，明确列出相应改动。不把业务页面集中写入 `App.vue`。

新增依赖前检查现有能力并说明选择依据；多人需要同时调整依赖时，由约定的集成人协调。锁文件通过 npm 正常生成，禁止手工拼接解决锁文件冲突。

## 样式、状态与权限

- 组件样式默认使用 `<style scoped>`。需要全局生效的样式必须说明影响范围；全局重置、主题变量与基础样式集中维护。模块不要在全局样式中直接改写所有 `button`、`table` 等标签，避免影响其他页面。
- 预约筛选、审批表单、工单编辑等业务状态放在所属模块。登录身份和确需全局共享的状态集中维护；不得直接修改另一模块的状态，也不通过无归属的全局对象传递业务数据。
- 路由使用已接入的 Vue Router 4。当前未安装状态管理和 UI 依赖；需要引入时，在相应任务中说明用途和评审范围，按已确认的决定实施。
- 登录过期、退出登录和身份切换的处理集中维护，并清理相关用户状态。前端权限判断用于页面、导航和按钮展示；实际身份、院系范围和操作权限必须由后端校验。

## API 与跨模块集成

- 按评审后的契约在各模块 `api.ts` 中封装业务请求，公共请求配置放在 `shared/api/`。字段、稳定 ID、错误语义和时间格式遵守共享契约，不在各模块自行定义互不兼容的格式。
- API 地址使用统一、可配置的入口，不把本地端口、公网 IP 或服务凭据写死在业务组件中。开发代理和部署反向代理的变更按公共配置评审；当前它们尚未配置，不能假定已可转发业务请求。
- 跨服务写回由后端完成。例如 M2 审批通过后，由 M2 调用 M1；前端不通过连续调用两个服务来替代该一致性流程。
- 新增或变更公共组件、请求处理或权限状态时，列出使用方并核验受影响页面；接口字段变化更新共享契约，在本模块交接中列出消费方影响，由各业务模块在各自授权任务中调整实现和记录。

## 分支、合并与验证

- 遵守根目录的任务模板和分支约定状态。每项任务限定范围，以小批次 PR 交付；多人并行时优先各自在模块目录内修改，及时同步已评审的公共变更。
- 提交前检查差异，避免把无关的全局格式化、依赖升级或其他模块重构混入业务任务。新增公共改动时，在 PR 中说明原因、使用方、兼容性和验证结果。
- 合并冲突由人确认并处理。代理应报告冲突文件、双方改动意图与需要决定的问题，不自行选择一方覆盖；人工处理后重新运行检查，并验证受影响页面。
- 请求评审前运行根目录 `bash scripts/check.sh`。Vue 类型检查和构建只能证明工程可构建；业务任务还须按验收条件验证相关页面及真实 API 行为，不能只凭构建通过宣布业务完成。
- 页面变更检查正常、加载、空数据、错误和无权限等适用状态，并检查窄屏及键盘操作。公共样式、布局、组件或登录变更须同时检查受影响模块，不能只看当前页面。
- 自动化测试应验证可观察行为，不能 mock 掉被测逻辑或只断言常量；不为凑测试数量创建占位测试。
