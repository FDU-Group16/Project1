# ADR 0003：M1 与 D-02 首版实施规则

日期：2026-10-22。状态：**本次用户确认实施；团队集成评审待完成**。这不是对 ADR0002 长期分工的批准。

## 范围和依据

用户要求完成 M1 和 M1 负责的 D-02，按需求提交且仅在 m1 分支；D-01/03/04 保留接口依赖。用户明确选择以下默认规则：Web 编码签到、首版本地账号/站内通知方向、最长4小时可配置、开始前取消、M2 与个人预约冲突返回409、维修保留既有预约并禁止新增。由于身份和通知不在本次范围，本地账号及站内通知真实实现留给提供方，不以消费方替身替代验收。

## 方案与取舍

继续 PostgreSQL 独立 schema/账号与真实 HTTP 服务边界，避免引入不兼容的内存或 SQLite 正常存储。单体同库直连方案代码更少，但违反跨服务约定；不采用。SQL 迁移在服务启动时按版本串行应用，种子是独立命令，默认不生成业务数据。技术公共层只封装数据库、时间和错误格式。

M1 默认向未来7天开放预约（环境可配置），预约开始必须为未来的整点，结束整点且晚于开始；每用户和每座位不能有重叠有效预约，边界为 UTC [start,end)。按北京时间展示、房间开放时间按 Asia/Shanghai 每日整点和星期计算。默认4小时上限可由管理权限调整。

房间每日签到码使用专用服务端秘密与房间/当地日期计算，管理端屏幕展示；学生在 [开始,开始+15分钟) 输入。验证码和令牌不得进入日志/审计。动态码不能完全防代签，人工纠错及更强验证需后续团队评审。

未签到规则为开始前15分钟提醒、后10分钟提醒、后15分钟自动取消/释放/违约。持久化发件箱支持重试；错过提醒窗口不补发过时提醒，无签到违约仍补处理。通知接收、实际送达和模拟接收必须分别显示。无自动惩罚或信用封禁，避免未经授权加码。

注销主数据采用不可逆软注销，保留ID与历史引用；停用可恢复。主数据变更不抹去历史预约，搜索/新预约使用实时权威数据；跨服务更新存在读取与事务间窗口，需在团队集成时评估版本/事件协调。

M2 ACTIVE 若与既有有效个人预约重叠则409，不能清除预约；M3 ACTIVE 保留既有预约并阻止新预约。多来源取并集，释放某来源不能清除其他限制；版本墓碑拒绝乱序请求。M2/M3 消费方不在本任务范围，提供方 HTTP 测试不等于业务端到端验收。

## 验收与责任

验收覆盖权限/院系、并发冲突、时间边界、错误验证码、重复与乱序、调度重启、依赖失败、软注销与迁移重放。每项代码/契约/测试/状态同批按需求提交。M1 集成；D 子域与 Web 公共、schema 变更由拟议责任组和受影响消费组在合并前人工评审，人员、PR与部署未登记。
