# ADR 0002：公共层 D 的归属与变更责任

- **状态**：Proposed（待项目组讨论；尚未达成共识）
- **日期**：2026-10-22
- **决策范围**：D 公共层的开发分工、公共前端配合、首期集成、公开契约治理与故障责任
- **关联需求**：`D-01～D-04`、`E-09`；M1 消费方边界关联 `M1-01～M1-08`、`X-01～X-04`
- **依据**：[任务书](../../任务书.pdf)第 1 页「公共层 D 的归属」及第 2–3 页的评审、集成和交付要求

## 背景

项目组约 6 人，至少分为 M1、M2、M3 三个模块组。D 包含身份/RBAC、空间和座位主数据、通知、操作审计等能力；四个模块共用同一组开发、测试和生产环境。任务书允许由一个模块组承担 D，或按子域拆分，但要求说明工作量、契约治理、故障责任与组内共识过程。

当前架构规划中，D 是独立的 `d-api` 服务。独立部署边界并不等于可以把公共层无人负责；同时 M1 已有较多明确业务需求，直接将全部 D 交给 M1 可能造成明显负担。

## 候选方案

| 方案 | 优点 | 主要代价 |
| --- | --- | --- |
| A：某一个模块组独自负责 D | 单一责任人清晰，接口变更集中 | 该组承担两块工作；其他模块对公共契约缺少直接维护权，容易排队 |
| B：D 按子域分给三个模块组，设置跨组评审规则 | 负担分散，子域贴近主要使用者；契约可共同治理 | 同一服务多人修改，需要明确代码边界、集成负责人和故障处理方式 |
| C：另设专职 D 小组 | 公共层专业化，责任清晰 | 约 6 人时会削弱三个业务模块的人力；交付节奏可能受 D 瓶颈影响 |

## 拟议决定

**建议采用方案 B，仍须项目组确认。** D 按子域分给三个模块组，`d-api` 保持单一独立服务。建议由 M2 组兼任 D 首期集成协调组，协调服务入口、契约汇总、公共基础设施和联调；各子域仍由对应主责组维护。长期发布轮值、具体人员与首期协调结束条件另由项目组确认。

| D 子域 | 拟议主责模块组 | 负责的交付内容与边界 |
| --- | --- | --- |
| 空间、教室和座位主数据（D-02） | M1 组 | 房间登记、注销/停用、院系归属、开放时间与基础可用性；座位登记、注销/停用、稳定唯一编号、插座标记；公开查询/管理接口及对应管理页面。D 维护基础事实，M1 业务服务维护预约与有效可约状态 |
| 身份、RBAC 与权限矩阵（D-01） | M2 组 | 登录、退出、当前身份查询、会话过期及约定的续期处理；用户、院系身份信息、角色与权限；为各后端提供统一的身份校验方式。身份接入方式及账号管理范围先确定契约；各业务服务仍执行自己的资源范围与数据归属检查 |
| 通知服务（D-03） | M3 组 | 接收通知请求、执行发送、记录投递状态、失败重试与重复请求处理；首期共同确定一种通知渠道。提醒、审批超时或工单升级的触发时机由相应业务模块决定 |
| 操作审计（D-04） | M3 组 | 接收、保存和受控查询关键操作记录，覆盖操作者、动作、对象、时间和结果等必要信息；审计范围、访问权限与保留期限须共同确认。业务模块负责在约定的操作发生时提交审计事件 |

这只是**团队分工建议**，并未指定个人，也没有声称 M1/M2/M3 已接受。P1 开始前应核对每组工作量；若 M1 承担空间主数据后超载，可重新分配人员或调整子域，保留修订记录。

## M1 业务与 D 的责任边界

| 事项 | 拟议责任归属 |
| --- | --- |
| 房间属于哪个院系、开放时间、座位清单与插座标记 | D 主数据，由 M1 组维护，供各模块通过公开接口使用 |
| 某座位在某时段是否已被预约 | M1 预约业务 |
| M2 整室占用、M3 维修限制及其来源 | M1 接收网络写回并保存来源；M2/M3 负责本模块状态与发送请求 |
| 单次预约时长上限、取消规则 | M1 业务规则；未决规则先完成需求与验收确认 |
| 教室签到编码、签到校验与结果 | M1 签到业务；不与用户登录凭据混用 |
| 用户登录、身份凭据校验、角色与公共权限信息 | D 身份认证，由 M2 组提供 |
| 用户能否预约该房间、访问或修改该预约 | M1 后端依据可信身份、院系范围、资源信息和预约归属检查；前端展示不能代替授权 |
| 预约提醒和违约的触发时机 | M1 决定并处理业务状态，调用 D 发送通知 |
| 通知发送渠道、投递结果与发送重试 | D 通知，由 M3 组提供 |

房间主数据中的停用用于管理员维护基础可用性。M3 的维修下架与恢复通过 M1 的来源记录处理，不能用覆盖 D 房间可用性的方式替代；释放一张工单的限制不得清除其他有效维修、整室占用或基础停用限制。稳定房间/座位 ID、UTC 时间与 `[start, end)` 区间遵守根规则，具体字段与变更传播方式在共享契约中定义。

## 公共前端配合（拟议）

本分工遵守 [Web 协作规则](../../apps/web/AGENTS.md)，保持一个 Vue 应用。

| 范围 | 拟议维护与集成责任 | 目录与评审约束 |
| --- | --- | --- |
| M1 业务页面、M1 对统一登录的接入 | M1 组 | 业务页面与适配代码放在 `apps/web/src/modules/m1/`，使用公共登录状态和 HTTP 入口 |
| D 房间与座位管理页面 | M1 组 | 在具体任务中确定 D 管理页面的目录、路由和权限；不把主数据管理逻辑放入公共组件 |
| 统一登录页、公共身份状态、登录恢复、退出/过期清理 | M2 组 | 通过 `apps/web/src/shared/auth/` 等公共入口提供；不让其他模块导入 `modules/m2/` 私有实现 |
| 首版公共 HTTP 层及其认证接入 | M2 组负责首期集成，M1/M3 作为消费方评审 | 放在 `apps/web/src/shared/api/`，处理请求配置与公共错误，不承接预约、审批或工单判断 |
| D 通知与审计所需管理页面 | M3 组 | 按已确认的最小管理需求另定目录、路由和权限，不默认建设完整运营后台 |
| 根导航、根路由、公共样式、依赖及构建配置 | 修改方提出，相关维护者与受影响模块组评审 | 任务/PR 明确集成人及评审人；共享层不得依赖业务模块内部实现 |

M1 对 D 身份子域的首轮需求是：统一登录、可信且稳定的用户身份、院系信息、必要角色/权限，以及后端可用的身份验证方式。登录载体、有效期、退出/续期、`401`/`403` 和错误语义由 D 与公共前端契约统一约定；M1 负责页面接入与自身资源权限检查，不另建一套账号或登录状态。

## 首期集成与第一轮交付（拟议）

M2 组的首期集成协调包括服务入口接入、契约汇总、公共登录/HTTP 基础设施以及联调安排。各子域的实现、版本化迁移、测试、状态记录和根因修复仍由其主责组负责；集成协调不授予自动合并、发布或代改其他模块业务的权限。

以下是待拆成任务并评审的最小交付目标，不是当前可用能力；请求/响应字段、错误、鉴权及兼容性以届时 `contracts/` 中的版本化契约为准。

| 主责组 | 第一轮最小交付目标 | 验收重点 |
| --- | --- | --- |
| M1 组 | D 房间与座位数据定义及查询接口，覆盖稳定 ID、院系归属、开放时间、基础可用性和插座信息 | 可通过公开 API 查询；ID 稳定；基础可用性与业务占用含义分开；首次持久化使用可从空库重放的迁移与独立幂等种子数据 |
| M2 组 | 登录、当前身份、退出及供 M1/M3 使用的身份验证方式；公共登录接入；所需学生、运营管理员等测试身份 | 不使用真实学生数据；身份可由后端验证；失效或退出的会话按契约拒绝；刷新恢复、深链接返回和用户切换清理得到验证；业务侧越权测试由对应模块完成 |
| M3 组 | 通知请求与状态查询、基础审计写入接口；明确失败、重复请求与重试规则 | 可区分请求已接收与实际投递结果；重复请求按契约处理；审计真实保存且访问受限，不写入凭据或无关个人数据 |

登录方式、角色/权限矩阵、稳定 ID 规则、主数据变更传播、通知渠道与审计最小范围仍需确认。首轮完成前，M1/M3 与 D 身份、M1 与 D 主数据、各业务模块与通知/审计分别记录实际联调证据。提供方尚未实现时，消费方在自身状态文件记录缺口；页面原型或演示数据不能作为真实认证、通知投递或业务集成完成的证据。

## 契约与评审规则（拟议）

1. `d-api` 的公开 HTTP 契约以 OpenAPI 3.1 文档为源；契约、需求 ID 和实现同一个 PR 更新。共享包只放协议类型及通用基础设施，不在其他服务中复制 D 的业务判断。
2. D 子域改动至少由该子域主责组和一个受影响的消费组评审；跨子域、schema 或权限矩阵改动由三个模块组共同评审。评审人和实际批准规则需与组内分支保护设置一致。
3. 各服务只使用自己的数据库 schema、迁移及访问账号。M1/M2/M3 不直接读取或修改 D 的业务表；D 也不直接操作 M1 的预约或占用表。
4. M2→M1 审批占用与 M3→M1 维修下架是独立跨模块契约。M1 对写入来源和撤销结果负责，M2/M3 对本模块状态与发送请求负责；要定义幂等、失败重试和版本兼容后再实现。
5. 变更影响跨模块时，先更新契约和消费方测试，再合并生产者实现；测试环境一次发布全组兼容版本。发布期间通过环境锁或窗口防止集成测试误报。

## 故障责任与升级（拟议）

| 故障位置 | 初步处理责任 | 根因修复和验证责任 |
| --- | --- | --- |
| D 子域内部行为或数据 | 当前发布/集成负责人协助定位 | 对应 D 子域主责组；受影响模块组提供复现与回归测试 |
| M1/M2/M3 调用 D 的契约不匹配 | 调用方与 D 子域主责组共同定位 | 引入不兼容变更的一方修复，双方补契约测试 |
| M2/M3 状态已改变但 M1 写回失败 | 发起模块组先检查重试/补偿记录 | 发起模块组与 M1 共同处理一致性；按来源追溯并验证修复 |
| 生产发布引起的系统性故障 | 当次发布负责人按预案回退或隔离 | 相关子域主责组完成根因分析，项目组记录发布复盘 |

以上是职责划分，不代表任何人已被指派值班。具体轮值表、事故响应方式和发布审批人在项目组确认后补入运维文档。

## 需要记录的组内决策过程

在本 ADR 从 `Proposed` 改为 `Accepted` 前，项目组应记录：

1. 每个模块组对 A/B/C 的意见，以及任务量估算和主要依据。
2. 对接口变更评审人数、D 子域与公共前端归属、M2 首期集成职责及结束条件、后续负责人轮值的最终约定。
3. 仍有异议的内容、讨论结论、同意方式和参与人员；如未达成共识，继续保持 `Proposed`。
4. 最终责任人/组、决定日期、关联会议或 PR 记录，并同步更新 `AGENTS.md`、CODEOWNERS（若采用）与实施计划。

## 后果与复审点

采用方案 B 后，每组会维护业务模块和一部分 D 能力，公共契约更接近使用方，但 `d-api` 的发布仍是组级协同事项。第一次 Review 前检查工作量和接口评审是否形成瓶颈；第二次 Review 前根据实际故障与变更记录复审归属。任何调整都应新建或修订 ADR，保留决策理由。
