# 项目架构与分阶段计划（草案 v0.1）

> 依据：[课程任务书](../任务书.pdf)与[初始需求基线](requirements.md)。本计划供项目组评审和分工，日期与人员尚未确定。**当前阶段仅搭建基本框架、共享契约与项目规则，不实现 M1/M2/M3/D 的业务功能。**

## 技术栈与系统边界

| 层面 | 当前选型 | 用途与边界 |
| --- | --- | --- |
| 运行时与语言 | 后端 Python 3.12；前端 TypeScript | 选用各端常见的轻量工具；跨语言数据结构以评审后的 OpenAPI 契约对齐 |
| 后端 | FastAPI + Uvicorn；`services/m1`、`services/m2`、`services/m3`、`services/d` 四个独立 ASGI 入口 | 每个服务有独立业务边界、启动入口和公开接口；跨服务不读取对方内部表 |
| 前端 | Vue 3 + Vite Web 应用 | 任务书允许学生端使用 Web；管理端页面可在同一应用中按权限组织，具体页面后续设计 |
| 仓库 | 单仓库；后端 uv、前端 npm 各自锁定依赖 | 根目录 `pyproject.toml`/`uv.lock` 与 `apps/web/package-lock.json` 分别管理依赖；共享代码只放技术性基础设施，不放跨模块业务逻辑 |
| 数据 | PostgreSQL | 目标是共用一个实例、各服务独立 schema/账号与迁移历史；当前 Compose 只配置空实例，具体迁移工具待选，跨服务数据经公开接口获取 |
| 接口 | OpenAPI 3.1 | 各服务公开 HTTP 契约；请求/响应、错误、鉴权、状态来源和版本兼容规则在实现前评审 |
| 本地与测试部署 | Docker Compose | 一次启动 Web、四服务及依赖；测试环境部署应一次覆盖全组模块 |
| 流水线 | GitHub Actions | 提交/PR 构建和测试；`develop` 测试环境部署配置已编写、待远端验证；后续增加迁移、生产人工批准与回退 |

逻辑依赖为：Web → 各模块公开 API；M1/M2/M3 → D 的身份权限、空间座位主数据、通知或审计 API；M2/M3 → M1 的座位限制写回 API。M1 负责汇总个人预约、整室审批占用、维修下架等来源并给出可预约结果。D 提供空间和座位的主数据，不直接修改 M1 的预约事实。上述写回方向来源于任务书第 2 页，具体传输方式、冲突策略和失败补偿仍需契约评审。

### 当前框架阶段的完成标准

1. 四个服务与 Web 可独立启动；仓库提供后端与前端依赖安装、统一检查和各服务启动入口。当前健康检查仅证明 HTTP 进程可用，不验证数据库或业务功能。
2. `AGENTS.md`、需求基线、架构/决策记录和共享接口文档进入版本管理；接口文档能表达服务边界与尚未确定的字段/行为。
3. Docker Compose 可启动本地全栈基础设施；GitHub Actions 对提交和 PR 执行框架级构建/检查，并阻断失败构建。
4. README 写明本地启动、仓库结构、文档入口及当前没有业务实现的事实。
5. 不创建虚假的业务数据、业务路由或“通过但未验证行为”的测试。后续按需求 ID 逐项实现与验证。

## 依赖与决策顺序

| 前置事项 | 依赖方 | 为什么要先确定 |
| --- | --- | --- |
| D 归属方案和评审规则（[ADR 草案](decisions/0002-d-ownership.md)） | 所有模块组 | 公共契约的责任、变更评审和故障归属需清楚 |
| 身份来源与权限矩阵；空间/座位主数据 ID 与归属模型 | M1、M2、M3 | 学生可见范围、申请资格和工单资源引用依赖这些定义 |
| M1 的占用/下架写回契约及来源记录 | M2、M3 | 审批和维修状态必须有可调用、可追溯且可回滚的落点 |
| M2 审批状态机、超时和既有个人预约冲突策略 | M2→M1 集成 | 避免批准整室时错误覆盖已生效的个人预约 |
| M3 维修状态、验收及多工单并存规则 | M3→M1 集成 | 避免一张工单验收后错误恢复仍在维修的房间 |
| 时间、时区、开放窗口和调度语义 | M1 提醒、M2 撤销、M3 升级 | 三模块都有时限驱动行为，需要同一时间约定 |
| 迁移与种子数据方案、部署窗口或环境锁 | 集成测试与部署 | 保证从空库重放，避免部署中测试误报 |

## 分阶段实施

| 阶段 | 主要工作 | 退出条件与证据 |
| --- | --- | --- |
| P0：当前框架 | 建立单仓库、Web/四服务空架构、统一检查脚本、Compose、初始 CI；编写 `AGENTS.md`、需求/接口/ADR 文档；提出分支和评审约定供组内确认 | 满足上方「当前框架阶段的完成标准」；代码审查中可见清晰边界，无业务实现 |
| P1：需求与第一纵切 | 组内确认 M2/M3/D 细化需求和 D 归属；冻结首版 OpenAPI 契约；先完成 D 身份/主数据最小能力，再完成 M1 搜索、预约与必要的状态写回入口 | 需求 ID→实现 PR→有效测试可追踪；第一迭代功能可演示，形成第一次 Review 所需依赖与风险记录 |
| P2：主功能与集成 | 按已确认需求完成 M1 签到、提醒、违约、历史和统计；M2 审批；M3 工单；打通 M2→M1 与 M3→M1 两条链路，含回滚和来源追溯 | 合同测试、服务间集成测试通过；跨模块状态写回可在测试环境观察 |
| P3：交付流水线与数据演进 | 版本化迁移、幂等种子数据、自动测试环境部署、环境锁、生产人工审批、版本标记与回退演练 | 全新环境可经流水线部署；schema 演进、生产发布和回退有运行记录；完成第二次 Review 演示条件 |
| P4：验收与展示 | 对照全部需求 ID 完成验收与缺口清单；复查权限、并发、定时任务、审计及工程伦理；排练期末现场演示 | 任务书第 5 页所列全新部署、CI、迁移、生产回退、网络跨模块写回均能实际演示 |

P1–P4 的先后关系是依赖顺序，不是固定日期；各模块组可在已冻结的接口契约下并行开发。每次发布统一标记版本，并记录包含哪些需求 ID 和迁移版本。自然语言业务代理属于附加项，仅在主线验收稳定后单独评估。

## 协作与质量门禁

- 提交应对应任务/需求 ID，并说明变更原因。AI 生成的改动由人逐项审查后提交；人工处理合并冲突。
- 任何跨服务公开契约、D 公共层或 schema 改动，都经受影响的模块组评审；先更新 OpenAPI 与需求/ADR，再更改实现。
- 单元测试应围绕可观察行为；集成测试覆盖真实服务边界与数据库迁移。对关键测试故意破坏实现，确认会失败，避免无效断言。
- CI 先执行安装、静态检查、构建和测试，失败不进入部署。测试环境自动部署完整系统；生产部署等待人工审批，保留可回滚镜像、迁移兼容和版本信息。
- 通过环境锁或部署窗口串行化同组部署与集成测试，防止测试期间模块版本不一致。
- 需求、决策和风险随迭代更新；未完成的需求保留状态和原因。工程伦理议题（例如预约公平、院系限制、身份数据、违约记录和审计数据的必要性与保留期限）在设计评审中同步记录。

## 初始风险登记

| 风险 | 可能影响 | 当前缓解措施 / 待验证点 |
| --- | --- | --- |
| D 公共层归属未达共识 | 公共服务无人维护或多人同时修改 | [ADR 0002](decisions/0002-d-ownership.md) 保持 `Proposed`；在 P1 前记录组内决定与责任人 |
| M2/M3/D 规则不完整 | 接口反复变更、测试无法验收 | 先补角色、状态机、时限与异常流，再冻结首版契约 |
| 座位状态由多来源影响 | 重复占用、误释放、追溯困难 | 设计来源记录、幂等和只撤销本来源；覆盖并发与多工单场景 |
| 审批与个人预约时间冲突 | 既有预约被无提示覆盖 | 在 M2→M1 接口实现前先决策冲突策略并写入验收标准 |
| 定时任务和通知不可靠 | 违约、超时撤销、升级时点偏差 | 使用统一时区和可测试时钟；明确重试、幂等和失败可观测性 |
| 共用数据库实例导致跨服务耦合 | 绕过接口、schema 互相影响 | 各服务独立 schema/账号/迁移，禁止查询对方业务表 |
| 集成测试撞上部署窗口 | 假失败和难以复现的状态 | CI 环境锁或发布窗口，记录参与测试的镜像/tag |
| AI 生成的测试只有形式 | CI 绿色但行为不正确 | 审查断言对象，对关键流程做故意破坏验证 |
| 个人信息与违约记录滥用 | 隐私和公平性问题 | 权限最小化、记录目的和保留期限在 D 需求细化时确认并留下决策证据 |
