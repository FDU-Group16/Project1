## 方案及选择

沿用 FastAPI/Vue/PostgreSQL。M3 自有持久化存储、版本化迁移、工单历史和写回 outbox；使用 SQLAlchemy 支持 PostgreSQL 正式目标以及显式开发/测试 SQLite。SQLite 是本地开发便捷选择，不据此宣称 PostgreSQL 部署已验证。D 未提供身份/主数据接口，定义模块内依赖端口，默认运行拒绝业务访问；仅显式开发模式启用隔离的合成身份/房间目录。M1 使用已有 `0.1.0-proposed` HTTP 契约；开发替身只能明确启用，真实 HTTP 错误不回退。

比较直接同步调用：实现较短，但请求成功后进程崩溃会丢失回执；因此使用事务内持久化目标状态、稳定来源键和版本，worker 确认 M1 回执后完成维修/验收状态切换。超时/503 有界退避重试；401/403/404/409/422 记录失败，等待人工协调，不能当成功。每个工单独立释放自己的来源，不清除同室其他维修或 M1/M2 占用。

## 本轮可执行规则（M3 提案，非已获全组批准）

- 上报者提交有效房间、标题、描述和分类；身份来自服务端，拒绝客户端身份/角色字段。创建按操作者与 Idempotency-Key 幂等。
- 调度角色派给有效维修人员，REPORTED/ASSIGNED 可派单或重派，禁止上报者同时成为受派维修者；上报者可看自己的工单，维修人员可看自己的指派，调度者可看全部。其他对象返回 404 防枚举。
- 状态：REPORTED → ASSIGNED → STARTING_REPAIR → IN_PROGRESS → PENDING_ACCEPTANCE → ACCEPTING → CLOSED；STARTING_REPAIR/ACCEPTING 表示等待 M1 回执。验收拒绝回 IN_PROGRESS 且保留阻断。只有确认 ACTIVE 才进入维修中；确认 RELEASED 才关闭。
- 上报者在 REPORTED/ASSIGNED 可取消；维修开始后禁止取消绕过验收。验收由上报者执行，调度者不能代替上报者给自己验收；维修说明/拒绝原因必填。
- CLOSED 后上报者可评价一次，整数 1～5 分。评价仅相关参与者可见。
- 默认派单 SLA 从上报起 24 小时，维修 SLA 从首次派单起 48 小时，可配置；ASSIGNED/STARTING_REPAIR/IN_PROGRESS 均计入维修 SLA，完工待验收与恢复同步无自动验收时限。首次派单和验收拒绝分别开始新阶段，重派不刷新维修时限；验收拒绝从拒绝时起重算 48 小时并保留原升级历史。以服务端 UTC 时钟判断 `now >= dueAt`。升级是独立标记，不替代维修状态；每阶段超时只产生一次升级记录，通知送达需 D 联调，不能伪称已通知。
- 修改附带预期 `version` 防止旧页面覆盖并发变更。网络写回重试保持 sourceId/revision/完整请求及关联 ID；校验回执来源、房间、版本和目标状态。

## 验收标准

1. HTTP 创建、查询、派单、维修、完工、驳回返工、验收、评分及取消可演示；身份/资源权限、非法状态、空白/过长/额外字段被拒绝。
2. 重复创建同键同内容返回同一工单，不同内容 409；旧版本修改 409；重启仍能查询工单和待处理写回。
3. 完工与驳回不释放；验收仅发本工单 RELEASED。M1 不可用时显示待同步/失败，不能声称完成联动。
4. 超时扫描到边界即升级且重复扫描不重复记录；关闭/取消工单不升级。
5. 本地网络测试验证真实 M3 HTTP 客户端发出的契约请求及超时/错误回执处理。提供方为测试替身的证据须标注，M1 座位与来源的真正验收仍待 M1 组。
6. 空库迁移及重复迁移通过；正常模式不接受演示身份，用户输入不能充当可信角色。
7. 运行根 `bash scripts/check.sh`、M3 行为测试及至少一次变异验证；前端检查加载/空/失败/权限、窄屏和实际 HTTP 流程。
