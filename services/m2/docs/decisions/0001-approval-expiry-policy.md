# M2 决策提案 0001：审批、截止与资源清理政策

- 日期：2026-10-23
- 状态：**Proposed / 待 M2、M1 与 D 相关负责人评审**
- 关联需求：`M2-01`、`M2-02`、`M2-03`、`X-02`、`X-03`、`X-04`
- 提案人：角色 B 的开发批次；不代表用户、队友或项目组已经批准

## 背景

课程需求只规定申请资格、多级审批和超时撤销，没有给出审批层级、管理范围、截止公式、资源占用时点或冲突恢复规则。M1 写回契约仍为 `0.1.0-proposed`，D 的身份与主数据契约尚未建立；本提案用于形成可评审的共同输入，不授权业务发布。

## 提议决定

1. 固定两级审批：一级按申请人院系，二级按房间管理范围；审批人分别需要 `m2.approve.level1`、`m2.approve.level2`，且禁止审批自己的申请。
2. 申请资格由可信身份中的 `m2.apply` 和经验证的房间开放范围共同决定；浏览器不得自报角色、院系或管理范围。
3. 截止时间采用 `min(提交时间 + 24 小时, 使用开始前 30 分钟)`，比较使用带时区的服务端时间，`now >= deadline_at` 即过期；参数可配置但语义保持一致。
4. 待审批不占用 M1 资源。二级最终通过先进入 `RESOURCE_PENDING`，持久化审批意图和 ACTIVE 命令；M1 返回并验证匹配成功、且确认事务时仍未截止后，申请才成为 `APPROVED`。
5. 不挤占已有个人预约。明确占用冲突时先持久化更高版本 RELEASED；确认清理后，未截止则回到二级待审，已截止则进入 `EXPIRED`。
6. 未知网络结果通过同一来源、revision、请求体和 correlation ID 重放确认；不得用新 revision 掩盖不确定结果。
7. `RESOURCE_PENDING` 到达截止后停止安排旧 ACTIVE，建立或复用更高 RELEASED，并将恢复目标单向提升为 `EXPIRED`。只有匹配的 RELEASED 成功后才能结束过期流程。
8. worker 每 60 秒扫描一次，由独立受管理进程运行，使用共享命令仓储的 claim/租约和有界退避；不得依赖 Codex 自动化或浏览器页面。
9. 申请人仅能撤回两种待审批状态；批准后的取消不属于首期范围。
10. 通知/审计采用事务 outbox 或等价可靠投递；业务成功不因通知失败回滚，但投递状态和失败必须可观察。公共接口未就绪时只保留本地事实并标记阻塞。

## 不变量

- 处于两种待审批状态的申请必须从未发送 ACTIVE，或此前 ACTIVE 已由更高版本 RELEASED 确认清理。
- 每次逻辑批准唯一关联原审批人、任务、意见、expected version、幂等记录、operation 和 ACTIVE 命令；worker 不能冒充审批人。
- 旧 ACTIVE 成功不得覆盖更高 RELEASED、过期目标或终态。
- 每个状态变化增加申请 version；M1 revision 是另一条单调序列，不混用。
- 申请、任务、审批记录、幂等意图和资源命令在需要原子性的步骤中共用同一 M2 UoW。

## 被否决前不得默认采用的替代方案

- 一级通过即占用资源：会使尚未完成的申请提前影响 M1。
- M1 超时后假定未生效：无法处理“已应用但响应丢失”。
- 冲突时直接回待审或过期：可能遗留已经生效的来源阻断。
- 每次扫描提升 RELEASED revision：会造成无界版本增长和回执竞态。
- 在每个 Uvicorn worker 内启动扫描器：会产生不受控的重复 worker。

## 评审与落地门槛

- M2 确认审批层级、撤回、截止和恢复策略。
- D 身份/权限与房间主数据负责人确认可信声明和范围语义。
- M1 确认占用冲突、409 分类、有限时段响应字段及服务认证。
- A 将共同状态、端口、UoW、资源命令仓储和迁移链落实为唯一 M2-BASE；B 核对后再实现 B1。

未完成上述评审时，只允许用本提案继续测试设计和接口评审，不得声称业务规则已定稿、真实服务已可用或集成已经通过。
